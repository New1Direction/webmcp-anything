0Executive thesis

wmcp.sh's durable bet is not "own the WebMCP/MCP namespace" (both are now governed standards under the Linux Foundation and W3C — that land-grab is lost, and the near-identical webmcp.sh playground run by the canonical WebMCP-org is a live brand-confusion liability) but "be the only layer that makes any consumer URL both AI-citable AND agent-callable-with-auth, with a self-serve till at every point of capture." The codebase already has the two genuinely hard-to-copy assets — a no-spec, any-URL 5-tier extraction engine and an OAuth-vault MCP proxy that injects and refreshes credentials agents physically cannot manage themselves — wrapped in a production-grade Stripe rail and ~99 GEO-ready pages. The strategic failure is purely product/pricing: of three advertised revenue lines, only the $29 API plan can charge a card without a human, the word "Pro" names two products 34x apart, and the demand-capture surface points at a sales form instead of a checkout. The first principle: turn the existing free flywheel (auto-indexed directory + free probe) into instant self-serve revenue on BOTH the directory and the service, while quietly building the metered OAuth-proxy moat that competitors are one product decision away from copying. Speed matters — the Chrome 149 WebMCP origin trial (June 2, 2026) opens a 1-2 quarter window where brands want readiness before in-house expertise exists.

2Current state — the honest read

The product is a well-built demand-capture machine with the cash register in a different room. The Stripe self-serve path (checkout, signed webhook, key issuance, idempotent recovery) is genuinely production-grade, but it sells exactly one thing: the API "Pro" plan at $29/mo. The other two advertised revenue lines earn $0 automatically — the managed service ($499/$999/$4,999) posts to a KV lead vault with no Stripe code and "Approve via email + Stripe invoice" as a literal process step, and the directory verified/featured badge is set only by a manual x-admin-token KV flip with no buy button anywhere. Pricing is incoherent in a user-visible way: the SEO/managed surface quotes "Pro $999/mo" across ~30 files while /dashboard sells "Pro $29/mo" — the same word, 34x apart (the managed.ts "$29/mo value" line is technically correct bundling language, so the fix is renaming, not relabeling). There is a hard conversion desert: free=100 reads/day and zero executes jumps straight to $29 with nothing between, and from $29 there is no in-product path to the $999/mo managed tier — the two funnels never cross-link. The auto-indexed /u/<slug> and /directory pages render unmoderated scraped brand content with no ownership claim and only host+path slugs, creating trademark exposure. The Anthropic provider rides the Claude Code client_id (self-labeled gray-area, ToS-revocable) and AGENTS.md flags it not-for-paying-customers. There is ZERO analytics anywhere in worker/src, so traffic-to-revenue is literally unmeasurable — the team is flying blind on whether 99 pages convert. Two security preconditions gate any revenue scaling: the unsigned-webhook fallback (only console.warn when STRIPE_WEBHOOK_SECRET unset) lets forged events mint paid keys, and a single TOKEN_ENC_KEY encrypts every user's OAuth tokens.

4First principles

The reasoning the strategy is derived from — not preferences, but constraints the product's actual position forces.

1

The defensible asset is credential custody and the auth dance, not URL extraction.

Shopify-JSON, JSON-LD, and OpenAPI walking are reproducible in a weekend; the OAuth-vault MCP proxy (token custody + proactive refresh + DCR/PKCE for arbitrary upstream MCP servers) is the one surface with real switching cost. Lead the moat narrative and pricing there, and treat extraction as the free top-of-funnel that feeds it.

2

Every dollar must be collectable without a human in the loop, or it is not real revenue.

The manual admin-KV-flip badge and email-invoiced managed tiers are theater. Any recommendation must wire the existing Stripe pipeline (extend the Plan type, branch the webhook) so the card charges and the entitlement provisions automatically — the single source of truth is auth.ts:16, so every new SKU starts there or is uncheckoutable by construction.

3

You cannot price, tune, or defend a funnel you cannot measure.

With zero analytics, the revenue estimates in every proposal are unfalsifiable. Minimal instrumentation (a KV counter or Cloudflare Analytics Engine event on /u, /directory, probe-run, checkout-started, paid) is a prerequisite for the IndexNow/featured/metering bets, not a nice-to-have — it is the highest-leverage quick win.

4

Trust and ownership are the scarce goods in a directory of auto-indexed brand URLs.

A forgeable admin-click badge has no defensible value and amplifies trademark liability; an ownership-proven, re-tested 'agent-ready Verified' badge is both the only directory asset worth paying for and the legal precondition for charging. Ownership proof must gate any paid badge purchase, and a delist/opt-out path must exist on every scraped page.

5

The namespace race is lost; the readiness-and-execution race is open and time-boxed.

Stop positioning as 'WebMCP/MCP' (governed standards, owned in search by the standards bodies; webmcp.sh is a one-character competitor). Position as the independent enabler that makes any site cited AND callable. The Chrome 149 origin trial (June 2026) and x402 facilitator fees only starting Jan 2026 create a narrow window to establish the readiness service and a metered facilitator before incumbents (Composio, Arcade, Pipedream, Rye) extend into arbitrary-MCP territory.

6

The category prices on free + usage, never on a setup fee anchor.

Every self-serve incumbent (Composio $29, Arcade $25, Gram $29) anchors a free tier then meters; agencies charge $8K-$80K for the same custom-adapter deliverable wmcp.sh sells for $499. The pricing ladder must fill the free-to-$999 desert with a $25-$99/mo self-serve rung, raise the productized fix toward the agency floor, and convert hard quota caps into billable overage rather than churn.

Core engine & adapters (5-tier read chain, execute chain, crypto adapters, OAuth-vault MCP proxy, token vault, cron seeder)

The "5-tier adapter chain" in worker/src/index.ts:1024-1185 is real and runs in this order on GET /api/v1/tools: (1) cache, (2) Shopify direct .json fetch, (3) OpenAPI spec ingest, (4) five HAND-CURATED crypto adapters (coingecko/dexscreener/pyth/defillama/chainlink — NOT auto-extracted, see coingecko.js header), (5) HTML-fetch + JSON-LD, (6) Haiku LLM fallback, else 404. Most of the "moat" is commodity: Shopify (adapters/shopify.js) just hits the public /products/{handle}.json and reshapes it; JSON-LD (adapters/jsonld.js) reparses schema.org any scraper already reads; OpenAPI (adapters/openapi.js) is a thin spec-walker. The two genuinely differentiated assets are (a) the OAuth-vault MCP proxy (worker/src/mcp_proxy.ts) which transparently injects+refreshes a user's stored bearer token into ANY OAuth-protected upstream MCP server so agents like Claude.ai/Cursor can connect to /mcp/<provider> as if unauthenticated, and (b) the openapi_request live-execute path that auto-injects the caller's connected-provider token via token_resolver.ts. The LLM fallback's unit economics are sound: it sends signals-only (jsonld/meta/title, ~1-2K input tokens, capped at 5 jsonld blocks, max_tokens:1024) to claude-haiku-4-5, with a 30-day cache (index.ts:1169) — so amortized cost per URL is fractions of a cent and trends to ~$0 on cache hits. Adapter coverage breadth is narrow: serious live actionability exists ONLY for Shopify (add_to_cart etc.); JSON-LD and LLM tiers are read-only snapshots; OpenAPI is generic but YAML-blind (JSON specs only, openapi.js:45). The single most monetizable capability competitors lack is the OAuth-vault MCP proxy + shared-tenant mode, not the URL-to-tools extraction.

What works
  • 5-tier read chain dispatches correctly and falls through on failure (index.ts:1038-1184); each tier caches with a sensible per-adapter TTL (Shopify 1h, OpenAPI 24h, crypto 60s-24h, JSON-LD 6h, LLM 30d)
  • Shopify adapter (adapters/shopify.js) is the only fully live-actionable path: get_product/get_price/check_stock/list_variants/add_to_cart, with re-fetch handlers and a CHROME_UA to defeat 403s — and it powers the cron auto-seeder
  • OAuth-vault MCP proxy (mcp_proxy.ts) is production-shaped: strips hop-by-hop + cf-* + cookie headers, preserves mcp-session-id for stateful Streamable HTTP, proactively refreshes tokens within 60s of expiry (REFRESH_SKEW_MS), handles rotating refresh tokens, and supports DCR (RFC 7591) + PKCE so new MCP providers need zero env config
  • Token vault (token_vault.ts) encrypts access+refresh tokens with AES-GCM-256 (random 12-byte IV per blob) rather than plaintext KV — standard SaaS posture for this scale
  • LLM fallback (adapters/llm.js) is cost-disciplined: signals-only payload (not raw HTML), forced tool_use schema, cache_control:ephemeral on the stable tool def, 30-day result cache, and it shifts inference cost to the caller's own Claude Max/Anthropic OAuth token when connected (index.ts:1137-1158)

MCP server registry / directory competitors and how they monetize — and the gap wmcp.sh can own.
Key findings
  • Directories monetize hosting/compute/gateway, almost never the listing itself. The biggest commercial players (Glama, Composio, Smithery hosted, mcp.run/TurboMCP) make money by running/proxying servers (per-instance hosting, per-tool-call gateway billing, AI credits, enterprise self-host), not by charging for catalog placement. The directory is a top-of-funnel loss-leader feeding a hosting/gateway business.
  • The official MCP Registry (registry.modelcontextprotocol.io, launched preview 2025-09-08, ~2,000 entries by Nov 2025, +407% since launch) is a deliberately NON-commercial, metadata-only metaregistry under the Linux Foundation / MCP steering committee. It hosts no code and no monetization, and explicitly invites 'sub-registries' (opinionated marketplaces) to build on top — i.e. the official layer is commoditized plumbing and the value-add/curation/trust layer is left open for others.
  • Scale is large but quality is the universal pain point. PulseMCP lists ~16,000+ servers, Glama ~26,000 raw (filters to ~11,415 real, removing clones/forks/empty), Smithery ~3,305+ servers / 7,300+ tools. Across the ecosystem there are ~19,000+ servers 'in the wild' but only ~2,300 are vetted/public in the official + Anthropic/GitHub curated sets. Glama's own 2025 state-of-MCP note: 'no way to tell which ones work, which are maintained, or which will poison your agent's context window.'
  • Creator monetization is a real, acknowledged gap. Smithery pays creators $0 (no revenue share). Glama is still only 'working on a revenue sharing model... announced soon.' Independent marketplaces (MCPize) advertise 80-85% revenue share precisely because incumbents don't pay creators. Glama's own blog: monetizing servers is 'one of the most frequent conversations I have with MCP server authors' — and <5% of servers are monetized.
  • Listings today are static install instructions, not transactional. Directories list a server's name, package, repo, install command, and metadata (health checks, quality scores, security audits, schemas). Almost none let an agent CALL the listed tool directly from the directory with hosted auth — you still install/run the server yourself. wmcp.sh's '/api/v1/tools?url=' returns a live, agent-invocable tool array with a hosted OAuth/credential vault, which is structurally different from a catalog entry.
  • Trust/verification + private allow-listed registries is where enterprise money is moving. Glama notes enterprises 'increasingly request private registries of audited and allow-listed MCP servers on their own infrastructure' and calls it 'a big opportunity.' TurboMCP (the rebrand/redirect target of mcp.run) repositioned entirely as a self-hosted enterprise gateway with OIDC/RBAC/audit logs — a signal that the public servlet-registry model alone didn't monetize and the value migrated to verified, governed, enterprise deployment.

  • Move fast on the official Registry integration. Becoming a recognized value-add sub-registry (consuming registry.modelcontextprotocol.io, adding verification + callable + auth) is a first-mover land-grab before larger players (Glama, GitHub) fully own the 'trusted sub-registry' slot.

What converts to recurring revenue = (a) captured buyer-intent/lead data sold back to vendors, (b) usage-based/metered billing where you sit in the transaction path (take rate), (c) analytics/dashboards vendors renew for, and (d) done-for-you services with high ACV. Verified: mcpProxy:true appears exactly once in providers.ts (defillama, line 252), and that single provider REQUIRES a paid DefiLlama API subscription to function (scopeNotice, providers.ts:259). So today there is literally one metered surface, gated behind someone else's paywall. 'Bill on volume' presupposes volume that does not exist. The metering plumbing is the easy 20%; sourcing a sticky multi-provider catalog of OAuth-protected upstream MCP servers (each requiring DCR+PKCE validation, ToS review, and ongoing maintenance) is the hard 80% the proposal hand-waves as 'the only thin part.' This is mislabeled as effort L when the catalog work alone is L-to-XL and is the actual product.
  • consume() IS NOT A BILLING METER. Verified at auth.ts:118-135: consume() is a non-atomic KV read-then-increment using executionCtx.waitUntil for the write. It is eventually-consistent and races under concurrency — fine for a loose daily hard-cap, structurally wrong as the source of truth for money. Billing customers off undercounted/eventually-consistent KV counters invites disputes and revenue leakage. The codeHook 'extend consume() to feed metered billing' understates that you need a separate, reconcilable, idempotent usage ledger, not a reused rate-limit counter.
  • STRIPE METERING IS NET-NEW CODE, NOT A LINE-ITEM TWEAK. Verified: createCheckout (stripe.ts:27) is hardcoded mode=subscription with a single line_items[0] at quantity:1; there is zero metered-price, usage-records, or meter-events code anywhere in stripe.ts. The Plan type is free|pro|reseller only (auth.ts:16). Delivering this requires: metered Stripe prices, a usage-reporting job (Workers cron or per-call meter event with idempotency keys), reconciliation against the KV ledger, and Plan/PLAN_LIMITS/STRIPE_PRICE_TO_PLAN changes. The audit's own note that 'webhook accepts UNSIGNED payloads when STRIPE_WEBHOOK_SECRET unset' (stripe.ts:180) means the billing rail is not even safe to scale revenue on yet.
  • MONETIZATION REALISM IS WEAK BECAUSE THE BUYER/DEMAND IS UNPROVEN AND UNMEASURABLE. The audit states there is ZERO analytics instrumentation anywhere in worker/src and that free→paid has executes_per_day:0, so every proxy call is already paywalled at $29 with no proof anyone is calling it. You cannot meter usage you cannot observe, and you have no evidence agents are hitting /mcp/* at all. Pricing a usage meter on a surface with no measured traffic is hand-wavy by definition.
  • THE COMPETITIVE COMP IS ALREADY COMMODITIZED AT THE EXACT METER YOU WANT TO CHARGE. Arcade prices auth-challenges at $0.05 and executions at $0.01; xpay/AWE run ZERO-FEE gas-sponsored facilitators; Coinbase x402 facilitator is free for the first 1,000/mo then $0.001/payment. The 'in-path facilitator cut' is real but the per-unit price is racing to ~zero. A marginal-cost meter on proxied calls competes against free and sub-cent incumbents — thin margin unless the value is the credential custody (a per-managed-connection subscription), not the per-call cut.
  • DEFENSIBILITY IS REAL BUT NARROW AND TIME-BOXED. The OAuth dance + proactive refresh + DCR/PKCE genuinely cannot be trivially replicated in a week (verified: getFreshUpstreamToken refresh logic, token_vault AES-GCM, DCR support). BUT Pipedream Connect ($2/external-user), Arcade (Anthropic-co-announced MCP auth flow), and Composio already hold credentials and manage OAuth at scale — they don't do it for ARBITRARY OAuth-protected MCP servers yet, which is the genuine wedge, but they are one product decision away. The moat is 'we did the boring credential-custody work for many MCP servers,' which is a head-start, not a structural lock-in.
  • SECURITY PRECONDITION IS A HARD BLOCKER, NOT A SIDE-NOTE. Verified token_vault.ts:36-39: ONE AES key derived from SHA-256(TOKEN_ENC_KEY) for ALL users, and the audit shows TOKEN_ENC_KEY is dual-duty (also OAuth HMAC in session.ts). Scaling PAID credential custody on a single-key SPOF, with no key rotation (rotating it bricks all tokens), is a catastrophic-blast-radius posture for a product whose entire pitch is 'we hold your credentials.' This must ship before paid scaling, and per-user key derivation is itself non-trivial migration work.
  • SHARED_USER RESALE IS A TOS LANDMINE BAKED INTO THE PROXY. Verified mcp_proxy.ts:30-47 + 83-110: SHARED_USER_<PROVIDER> routes all callers through one operator account; the code's own comments admit most upstream ToS forbid single-account multi-tenant resale and one suspension kills everyone. The proposal correctly says sell per-user only — but the shared-tenant code path EXISTS and is the tempting shortcut to 'create volume to meter,' which is exactly the wrong way to manufacture the metered demand the revenue case needs.
Refinements (folded into final)
  • DECOUPLE THE TWO BETS AND PRICE THE DEFENSIBLE ONE AS A SUBSCRIPTION, NOT A PER-CALL METER. The durable switching cost is the CREDENTIAL CONNECTION (re-doing OAuth elsewhere is the pain), not the call volume. Lead with a per-managed-connection recurring SKU (Pipedream's proven $2/external-user model) which listMcpProxies (mcp_proxy.ts:251) can already count, and treat per-call overage as a secondary lever. This monetizes the actual moat (custody) and dodges the race-to-zero per-call price war.
  • BUILD A RECONCILABLE USAGE LEDGER SEPARATE FROM consume(). Do not bill off the KV rate-limit counter. Emit per-call usage events (with idempotency keys) to a durable store, aggregate on a Workers cron, and report to Stripe metered prices in batch — this also sidesteps consume()'s non-atomic race. Keep consume() as the hard-cap; add a parallel ledger as the billing source of truth.
  • GATE THIS BEHIND ANALYTICS + THE SECURITY FIXES AS PHASE 0. Instrument /mcp/* call volume FIRST (the audit confirms zero analytics) so you can prove demand before pricing it. Ship per-user key derivation and fix the unsigned-webhook fallback (503 in prod) BEFORE taking a dollar for credential custody. The proposal's own risk section says sequence after the directory SKUs prove the till works — make that a hard gate, not a suggestion.
  • PRODUCTIZE CATALOG EXPANSION AS THE PRIMARY DELIVERABLE WITH AN ACCEPTANCE BAR. Define a target list (5-10 OAuth-protected MCP servers with real demand — not crypto-niche, paywalled ones like DefiLlama), and a per-provider checklist (DCR works, refresh works, ToS permits per-user proxying, no shared-account dependency). Until ~5 non-paywalled providers proxy cleanly, there is no metered product. Re-scope effort to XL and front-load this.
  • MEASURE THE MOAT AGAINST ARCADE/PIPEDREAM/COMPOSIO EXPLICITLY. The only defensible claim is 'arbitrary OAuth-protected MCP servers with transparent refresh, zero per-app config via DCR.' Pin marketing/pricing to that exact phrase and ship it before those incumbents add arbitrary-MCP support. If any of them ships it first, the per-call meter has no premium left — so treat this as a speed race with a 1-2 quarter window, consistent with the WebMCP/x402 timing research.
  • DO NOT MANUFACTURE METERED VOLUME VIA SHARED_USER. Remove or hard-disable the SHARED_USER_<PROVIDER> path for any provider whose ToS forbids multi-tenant resale, and never use it to seed 'volume to bill.' Per-user connections only, enforced in code, or the revenue is built on a suspension-prone foundation.
  • FIX OR DELETE THE 'don't meter anthropic' CAVEAT — IT'S MIS-AIMED. Verified: anthropic (providers.ts:202) is NOT an mcpProxy provider (no mcpUrl/mcpProxy), so it cannot be metered via mcpProxyHandler anyway. The real exposure is the Claude-Code-client_id gray-area auth on the inference/openapi path, which is a separate subsystem. Keep the 'don't monetize the gray-area Anthropic auth' rule but stop framing it as part of the proxy meter — it signals the proposal conflated two code paths.
